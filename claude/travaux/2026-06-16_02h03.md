## 1. Contexte métier (à connaître absolument)

**Projet :** site **vitrine** d'un **service de batchcooking à domicile**. Emma se déplace chez les clients pour cuisiner leurs repas de la semaine.

Points décisifs déjà tranchés avec le client (NE PAS les remettre en question sans demander) :
- **Aucune vente / aucun paiement en ligne.** Le site **affiche** seulement les offres. Paiement en personne (espèces/CB via les propres moyens d'Emma). → site en **lecture seule**, aucune écriture publique.
- **Les `plats` ne sont pas vendus à l'unité** : c'est un **répertoire d'inspiration** ET l'**unité de tarification**. Chaque plat porte :
  - `cout_matiere_premiere_moyen` (coût ingrédients — sert à estimer les courses, **non affiché publiquement**),
  - `prestation` (prix du travail d'Emma), **fixe** ou **fourchette** (`type: "fixe" | "fourchette"`).
- **Les `formules` ont un prix FIXE** (forfait saisi par Emma, pas calculé depuis les plats).
- **Option courses** : si Emma fait les courses → supplément = **montant des courses + service** (champ `mention_courses` affiché tel quel).
- **Pas de témoignages, pas de collection `demandes`/formulaire en base en phase 1** → repoussés en V2. Contact = liens directs (tel/email/Instagram).

Le cahier des charges complet et à jour est dans **`base_connaissance/cahier_des_charges.md`** (modèle de données détaillé, contrats `data_contenu` par `type_page`, etc.). **Le lire en premier.**

## 2. Préférences du développeur (important pour collaborer)

- C'est un **développeur Flutter expérimenté**. Il exige une **Clean Architecture stricte** :
  **UI → UseCase → Repository** (l'UI ne touche jamais Firestore ni les repositories directement).
- Repository = **3 classes par entité** : mère abstraite + enfant `Fake…` (dev) + enfant `Firestore…` (staging/prod).
- Il aime qu'on lui traduise les concepts Next.js en analogies Flutter (ex. module singleton ≈ `get_it` ; React Context ≈ `Provider`/`InheritedWidget`).
- Il travaille avec **3 environnements distincts** : dev (fausses données locales), staging (son Firestore de test), production (Firestore du client).
- En **dev**, il est NORMAL et VOULU que vitrine et admin ne communiquent pas : chaque app a ses fausses données locales en mémoire.

(Voir aussi la mémoire projet : `user-flutter-clean-archi`.)

## 4. Les 3 environnements

| Env | Source données | Clés | Comment lancer |
|---|---|---|---|
| development | `mock` (fixtures) | aucune | `npm run dev -w vitrine` (ou `-w admin`) |
| staging | Firestore test | `apps/<app>/.env.staging.local` | `npm run dev:staging -w vitrine` |
| production | Firestore client | `apps/<app>/.env.production.local` | `npm run build:production -w vitrine` |

- Sélecteur : `NEXT_PUBLIC_DATA_SOURCE=mock|firestore` (défaut : `mock` hors prod, `firestore` en prod).
- Fichiers d'env **par app** (`.env.development` versionné = flags sans secret ; `.env.*.local` gitignorés ; `.env.*.example` versionnés).
- Chargement staging/prod via `dotenv-cli` dans les scripts.

## 7. Conventions & pièges à connaître

- **Layering non négociable** : un composant importe `@/lib/queries` (qui appelle `useCases`), jamais un repository ni Firestore.
- **Union discriminée des pages** : après `if (page.type_page !== "xxx") notFound()`, TS connaît la forme exacte de `data_contenu`. Toujours faire cette garde.
- **`firebase.ts` est lazy** : ne jamais réintroduire d'init au niveau module (sinon `auth/invalid-api-key` casse le build/dev en mock). Utiliser `getDb()` etc.
- **lucide-react v1** : pas d'icônes de marque. Vérifier l'existence d'une icône avant de l'importer.
- **`@batchcooking/core`** est en TS source (pas de build) → toute app qui le consomme doit le `transpilePackages`.
- **Tests rapides en dev** : `npm run dev -w vitrine` puis `curl localhost:3000/...`. Attention : React découpe `{var} texte` en nœuds séparés (`>3<!-- --> plats`) → un `grep "3 plats"` peut donner un faux négatif.
- **Commandes utiles à la racine** : `npm run typecheck` / `npm run lint` (tous les workspaces), `npm run build:vitrine`, `npm run dev:admin`.
